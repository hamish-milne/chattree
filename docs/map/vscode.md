# `extensions/vscode/`: the VS Code extension

**Purpose.** The first graphical front end: a thread graph in the side bar, a chat in the panel and a form for `harness.yml`. It is a workspace package (`pnpm-workspace.yaml`), separate from the root package because it has its own manifest and dependencies and is bundled for the VSIX. Reasons: ADR 35. The shared logic is in [`ui/`](ui.md).

**Status.** The graph view, the chat view (transcript, composer, status bar, model settings), the form field renderer and the browser preview exist, driven by the mock controller. The thread settings sheet (a gear in the chat header replaces the transcript with it: `harness.yml` pages for providers, limits, approvals, MCP servers, subagents, context and repository, and, for the thread, its instruction files) exists in the preview too. The extension host (`src/`) runs the real controller and shows the graph in the side bar and the chat in the panel; `pnpm --filter chattree-vscode build` bundles it into `dist/`. Run in VS Code, it is untested by hand: the smoke test in CI (wdio) is the check, and the extension host's bundle is checked to activate against a stub of the `vscode` API.

**Depends on:** `chattree` (the root package, through its `ui/model/*` and `ui/fixtures/*` exports), `preact`, `@preact/signals`, `marked`. The graph has a repository picker above it, a context menu (open, fork, rewind, merge, copy hash, delete thread) and a confirmation dialog for delete, a New thread button, a show-archived switch, "Initialize in <folder>" items in the picker for workspace folders that hold no conversation yet; above the composer a banner when the thread has no provider or an unapproved harness.yml. Runs of tool calls are drawn as one bordered group; each built-in tool has its own body (diff, numbered lines, terminal) chosen by `toolView`. A reference to a file (in a message, or the path of a tool call) is a button (`webview/chat/FileLink.tsx`): a click opens it as the extension's setting says, and a right-click offers the current file or the file as it was after that block's change. Markdown is rendered from tokens into Preact elements (`webview/markdown.tsx`), never as HTML: raw HTML is shown as text, links are limited to http, https and mailto, images show their alt text. Webview code imports nothing from Node, `vscode` or the harness.

## Layout

Each directory has its own `tsconfig.json`, because each runs in a different place (the type checker and the linter find the nearest one).

| Path | Role |
|---|---|
| `webview/` | The views (Preact). A view takes a model from `ui/model` and draws it; it keeps no state of its own and talks to nothing but its model. `webview/graph/` is the thread graph (the checked-out thread is marked with a monitor icon; the context menu can switch the workspace to a thread, asking what to do with uncommitted files); `webview/config/` is the settings sheet: common choices as buttons and labelled inputs (provider cards with a connection check, limits, compaction), granular settings as dense tables (approvals with expiry, MCP servers, subagent models grouped by provider with a switch each, reminder rules, instruction files). |
| `src/` | The extension host (CommonJS, bundled to `dist/extension.js` with the controller and harness inside; `vscode` is external). `extension.ts`: `activate` builds the controller on the workspace folders (read once; a change asks for a reload) and a `Bridge` (`ui/host/bridge.ts`), registers the two webview views (`chattree.graph` in the activity bar, `chattree.chat` in the panel) and the commands (show threads, show chat, new thread). `platform.ts` is the `Platform` over the VS Code API (open a file at a range, or a read-only `chattree-snapshot:` document for a file as an earlier commit had it; the clipboard; a file picker). `html.ts` is the webview page (CSP: scripts by nonce only; one bundle, the view chosen by `data-view`). Notices are shown as VS Code notifications, not drawn by a view. Views are not retained while hidden: a view that opens sends `ready` and the controller replays its state. |
| `webview/main.tsx` | The webviews' entry: the three models over `postMessage`, the view named by `data-view`. Bundled to `dist/webview/` by `tools/build-extension.mts`. |
| `media/` | The icon of the two view containers. |
| `preview/` | The browser preview: the views over a mock controller in a frame that stands in for VS Code, with a Dark+/Light+ theme switch (`themes.css` defines the `--vscode-*` variables VS Code would), a width slider and a log of the intents a view sends. Not shipped. |
| `web/` | The web client: the same views and the preview's frame without its mock controls, wired to a controller over HTTP (`ui/host/web-host.ts`). Not shipped; it is what the end-to-end tests drive. |
| `tools/` | `build-extension.mts` bundles the extension host and the webviews' page into `dist/` (`EXTENSION_OUT`); `build-web.mts` bundles the web client into `dist/web/` (`WEB_OUT` to choose another directory); `build-preview.mts` bundles the preview with esbuild into `dist/preview/` (script and one stylesheet); `serve-preview.mts` serves it on `127.0.0.1`; `gen-css-types.mts` writes the type declarations for CSS modules (`--check`, `--watch`); `dev.mts` runs the watcher, a rebuild on change and the server together (`pnpm dev` at the root). `.mts` because the package itself is CommonJS (the extension's output must be). |

## Working on a view

- Run `pnpm dev` (at the root) and open the address it prints; it rebuilds when a source changes. Or `pnpm --filter chattree-vscode build:preview` then `preview` for a single build.
- **Styles are CSS modules.** Each view has a `x.module.css` beside it, imported as `import css from "./x.module.css"` and used as `css.row` or `css.pv_card`; esbuild renames the classes per file, so a name cannot collide with another view's. `tools/gen-css-types.mts` writes `x.module.css.d.ts` next to each (committed, kept current by `pnpm dev` and by every build, checked by `test/ui/css-modules.test.ts`), so `css.pil` is a type error. `cn(...)` joins classes (`cn(css.row, active && css.active)`); `pick(css, `state_${s}`)` is the class for a state when the stylesheet has a rule for it. `webview/base.css` stays global: the shared primitives (`icon-button`, `primary`, `secondary`, `menu`, `chip`, `dim`) are plain strings, and a module styles them as `:global(.primary)`. Keyframes are per stylesheet. Select by role, label or `data-*`, never by class name (names are hashed): tests and scripts do the same.
- A view uses only `var(--vscode-*)` colours and fonts, so it follows the user's theme; add a variable to `preview/themes.css` when the view needs a new one (the values there are approximations of Dark+ and Light+).
- A page that uses signals must import `@preact/signals` once (the preview does), which installs the hook that re-renders on a change.
- A view's behaviour that is not drawing (what a click does, which actions apply) belongs in `ui/model` and is tested there.
- `test/ui/preview.test.ts` builds the bundle and checks it has no Node imports, no typebox and one copy of the signals core.
