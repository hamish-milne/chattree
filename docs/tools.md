# Tool loop and starter tools

Status: **agreed plan** (reviewed with comments; build not started). Build status goes in section 11 as the steps land.

## 1. Goals and non-goals

The goal is a coding-agent loop you can use from the CLI: the model asks for tools, the host runs them, the results go back, and the whole exchange lands in the Git history like any other entry. The loop stays small. Resume, audit, cost and branching already come from the transcript being canonical.

Goals

- A host-side tool loop that works for any adapter that reports `stop_reason: tool_use`, with no provider-specific code in the loop.
- Five leaf tools: `read`, `write`, `edit`, `run`, `script`. Enough to inspect and change a project and run its tests.
- Three meta tools that operate on chattree itself: `fork`, `subagent`, `merge`. They reuse `fork`, `spawnSubagent`/`finishSubagent` and `mergeFork`.
- Every call and result is recorded as entries, so a crash, an abort or `/undo` at any point leaves a history that verifies and can be resumed.
- A canonical tool format that all three provider flavours translate, with a live check to validate each.
- Safe by default: file tools stay inside the workspace, commands ask before they run, and the request, time and money limits apply to the whole loop.

Non-goals for this step

- OS-level sandboxing of commands. Approvals and a workspace boundary come first.
- MCP servers and user-defined tools. The registry is shaped so they can plug in later.
- Parallel execution of foreground calls. Results are recorded in call order. (Background jobs, section 3.5, are the concurrency story.)
- Search and web tools (`grep`, `fetch`). `run` covers search and the rest can wait.
- A TUI for approvals. The plain prompt the CLI has is enough.

## 2. What the library already provides, and the gaps

Most of the machinery exists. `requestStream` leaves exactly one thing to the host: running the tools and asking again.

Already there

- **Recording.** An `assistant` entry carries `tool_call` blocks (`call_id`, `name`, `args`, `args_raw` when the model sent invalid JSON). A `tool_result` entry carries `call_id`, `is_error`, `content` (text or a blob reference) and `truncated`.
- **Pairing.** The context builder matches results to calls. A call with no result is answered with a synthesized "tool did not run" error, a result with no call is dropped, consecutive results are grouped into one provider turn, and a half-received call from an interrupted response is replayed as a text note, never as a live call. A crash or `/abort` mid-loop cannot produce an invalid request.
- **Definitions** are pinned by hash in the agent setup (`pinDefinition`, `loadDefinitions`, `assertDefinitions`).
- **Mid-loop guard.** `inToolLoop` lets the setup-change logic refuse or ask about changes a provider forbids inside a loop.
- **Limits.** `max_requests_per_turn` and the money limits use the ledger, whose "turn" starts at a user entry, so every request in a loop counts toward one turn. `max_turn_seconds` is a deadline passed to each request.
- **Meta tools.** `fork`, `spawnSubagent`/`finishSubagent`, `mergeFork`. `subagent_result` is already treated as the result of the call that started the subagent, with a user-message fallback when no call is open; `fork_merge` is shown as a user message.
- **Crash and abort.** The journal, `recoverRequest` and `requestAbort`.

Gaps this plan fills

1. A tool registry in the host: name, schema, flags, an asynchronous `execute`, and the pinned definition.
2. The loop, with per-call approval and results recorded as each call finishes.
3. Result shaping: size cap, truncation, and keeping the full output recoverable without duplicating what the repository holds.
4. Results that arrive late or never: a tool running when the user aborts or the process dies, and background jobs that finish between turns.
5. A portable canonical tool schema, checked at pin time, and adapter behaviour for tool calls verified per flavour (section 3.6).
6. CLI rendering, approval prompts and notifications.

## 3. The loop

A turn begins with a user entry and ends when the model answers without asking for a tool.

```
append user ─▶ request ─▶ tool_use? ──no──▶ end of turn
                 ▲            │yes
                 │            ▼
        append tool_result ◀─ approve, then run each call in order
          (one per call)
```

Before every request the requests-per-turn, deadline and money limits are checked. After an abort or crash, calls without a result are answered with a did-not-run error.

### 3.1 Per-turn flow

1. Append the `user` entry (as `sendMessage` does today).
2. Run one request with `requestStream`. It commits an `assistant` entry, or an `interrupted` entry if cut off.
3. If `stop_reason` is not `tool_use` the turn is over; other reasons (`max_tokens`, `refusal`, `pause`) are reported as now.
4. Otherwise take the `tool_call` blocks in order. For each: look up the tool, validate `args` against its schema, ask for approval if needed, execute, and append one `tool_result` entry straight away. A malformed call (unknown tool, `args_raw` set, schema failure) gets an `is_error` result explaining the problem.
5. When every call has a result, go to step 2 with the same deadline.

**Results are written one at a time**, each its own commit. A crash after the second of three calls leaves two results and one unanswered call, which the context builder already answers with a did-not-run error.

**Order.** Foreground calls run in the order given, one at a time; results are written in the same order.

**Limits.** The loop adds none. The request and money limits stop it before a request is sent; `max_turn_seconds` is a deadline shared by all requests and tool runs in the turn. When a limit stops the loop with calls unanswered, they are answered with a did-not-run error and the CLI says which limit it hit.

**Abort.** `/abort` or Ctrl-C works as today during a request. During a tool run it aborts the tool through an `AbortSignal` (`run` kills its process group), records an error result saying it was stopped, answers the remaining calls with did-not-run, and ends the turn without another request.

**Crash recovery.** After a crash the transcript ends with an `assistant` entry whose calls may be partly answered. `/retry` and the next message both answer the unanswered calls with did-not-run and continue. A call that may have half-finished is never re-run automatically; only the model can decide to, with the error in front of it.

**Where it lives.** `harness/loop.ts`, so other hosts can use it. It takes the conversation, the registry, an approval callback and the request options, and yields events: the request events as now, plus `tool.start`, `tool.approval`, `tool.result`. `runTurn` in the CLI becomes a renderer of those events.

### 3.2 Result shape

Output over a size cap (starting point: 30 KB) is cut to head and tail with a marker and `truncated: true`. What the full output points to depends on its origin:

- **Already in the repository** (a `read` of a large file): the idea agreed in review was a reference (path, offset, length at the entry's commit) in place of a copy. **Deferred**: a `read` result is formatted (headers, line numbers, several files), so it is not a byte range of one file, and a reference would need the result re-rendered at read time from the file at that commit. Until then the result is stored as text, and the write pipeline's own size threshold turns a large one into a blob (identical re-reads share one blob). See the parking lot.
- **Not in the repository** (command output, job logs): a blob.

Offsets are bytes; line numbers are applied when rendering. The marker tells the model how to ask for more. Text only for now; image results are a follow-up.

### 3.3 Cost and limits of nested work

A child's spend is recorded on its branch and summarised on the merge entry; the plan is that it counts toward the parent's turn limit (see section 10).

### 3.4 Snapshots

No separate snapshot step: appending an entry already commits the workspace changes with it, so each `tool_result` entry's commit holds the files as that call left them. `/undo` and forks see the files as they were at that point.

### 3.5 Background jobs

A tool that declares itself background-capable can be started with `background: true`. Its executor is asynchronous: it returns a job handle at once and the call's `tool_result` says so (`started job j1`). The job keeps running in the host while the loop carries on. When it finishes the harness commits a `job_event` entry on the branch (a new entry type, shown to the model as a user message, like `fork_merge`) with the status, a summary and the output as a reference.

- Mid-loop: the event is delivered with the next request in that loop.
- Idle: the entry is committed either way. With `background.resume: true` in `harness.yml` the harness also sends a request so the model can react; without it (the default) the CLI tells the user at the next prompt (`background job j1 has finished; your next message will report the result`).

Three small tools manage jobs: `jobs`, `job_output` (read the log from an offset) and `job_stop`. Jobs live as long as the CLI process. After a crash, recovery commits a `job_event` marking each job lost.

### 3.6 Provider adapters and the canonical tool format

The loop is provider-neutral because every adapter translates the same canonical format. The plan makes that explicit instead of assuming it.

**Canonical definition.** `ToolDefinition { name, description, input_schema, flags? }` where `input_schema` is a **portable JSON Schema subset**: objects with `properties`, `required` and `additionalProperties: false`; arrays (including arrays of objects); `string`, `number`, `integer`, `boolean`, `enum`; `description` on any node. Not allowed: `oneOf`/`anyOf`/`allOf`, `$ref`/`$defs`, `format`, `pattern` and friends, because servers differ on them and local servers compile schemas to grammars. A small validator for this subset (`harness/tool-schema.ts`, no new dependency) runs at registration and pin time, so a tool outside the subset cannot be registered, and the same validator checks call arguments in the loop.

**What each adapter must do**, with a conformance test in `test/providers` for each:

- Translate the definitions unchanged (Anthropic `input_schema`; Chat Completions `function.parameters`; Responses `parameters`, currently `strict: false`, which stays because strict mode forbids optional fields).
- Return several calls in one response as several `tool_call` blocks, in order, with unique ids (Chat Completions servers may omit ids; the adapter makes them up).
- Turn invalid or empty argument strings into `args_raw` or `{}` as now.
- Convey several results for one assistant turn in the form the API needs (Anthropic: one user message; Chat Completions: one `tool` message each; Responses: `function_call_output` items), and `is_error` where the API has a flag.
- Replay reasoning blocks that must accompany tool calls, per provider, unchanged.

**The live check** (`tools/live-check.ts`) grows in two stages. The existing `tool-call` scenario covers one made-up tool; these use the real definitions.

Stage A, at the first checkpoint (after the loop and leaf tools exist, section 9 step 4):

- `tools-schema`: send all starter definitions; the server must accept them, and a prompt that needs `read` must produce a call that passes the schema.
- `tools-parallel`: ask for two independent reads; if the model emits several calls they must have unique ids and round-trip.
- `tools-reliability`: a few prompts for `run` command lines (pipes, globs, redirects); report how many calls were valid.
- `tools-edit`: five edit tasks in fresh temporary workspaces through the real loop (one line, two places, delete a block, insert and append, an edit after an edit), scored by whether the file ended up right, so a call that is valid but changes the wrong lines counts as wrong.
- `agent-loop`: end to end through the real `harness/loop.ts` in a temporary git workspace, with approvals auto-granted by the test: read a file, edit it, run a command, and assert the file and the history (it verifies).

Stage B, after the meta tools: `agent-subagent`, `agent-fork`, and a background `run`.

Each scenario skips, not fails, when the model does not support tools. `--record` saves the events so fixtures for offline conformance tests can be made from real runs. The paid runs are yours to start; they join the deferred live verification in the parking lot.

### 3.7 Tool calling conventions

How much of a tool's schema a model is actually shown depends on the model and on the server it is reached through. Ollama, for gpt-oss, prints a list as `any[]` and an object as `Record<string, any>` and drops what is inside, so the model guesses nested fields (step 4f). Each model therefore has a **tool convention**, in its catalog entry (`ModelInfo.tool_convention`) or under `providers.<name>.models.<model>.tool_convention` in `harness.yml`:

- `full` (the default): any schema in the portable subset.
- `flat`: only a tool's top-level properties are reliably shown, so a tool must have scalar properties (or lists of scalars) and nothing nested.

A flat schema is just a JSON Schema in that subset, not a second notation, so it keeps its per-property descriptions, goes through the same validation and coercion, and works on `full` models unchanged. The rule is therefore one-directional: every flat tool can be given to every model; a tool with nested arguments can only be given to `full` models. `flatProblems(schema)` (`harness/tool-schema.ts`) says why a schema is not flat, and `runLoop` refuses with `ToolsNotSupported`, naming each tool and the reason, when the agent's model is `flat` and the registry holds a tool that is not. The starter tools are all flat (a test keeps them so). The convention is looked up at request time, so a model change needs no setup change. `tools-nesting` in the live check sends a tool with a list of objects, scores whether the model fills it exactly right without repair, and prints the value to set. Not built, parked: a second, hand-written schema per tool for the convention, and the conventions `text` and `raw` (see the parking lot).

## 4. Starter tools

Each tool is a definition plus an asynchronous `execute` in the host, pinned in the agent setup. Paths are relative to the thread's worktree, which is the workspace.

| Tool | Input | Approval default | Background |
|---|---|---|---|
| `read` | `path`, `offset?`, `limit?` | allow | no |
| `write` | `path`, `content` | allow | no |
| `edit` | `path`, `version`, then `start` and `end` or `after`, and `content?` | allow | no |
| `run` | `command`, `timeout_seconds?`, `background?` | ask (allowlist skips) | yes |
| `script` | `script`, `timeout_seconds?`, `background?` | ask, always | yes |
| `fork` | `name`, `message`, `auto_run?` | allow | with `auto_run` |
| `subagent` | `brief`, `name?`, `background?` | allow | yes |
| `merge` | `branch`, `summary` | ask | no |

`jobs`, `job_output` and `job_stop` are always allowed.

### 4.1 Leaf tools

**Flat arguments.** `read`, `write` and `edit` each take one file and flat, top-level arguments, no nested lists. Reason: Ollama renders every array-of-objects in a tool schema as `any[]` in the prompt of models that use the Harmony format (gpt-oss), so the model never sees the inner fields and guesses them (step 4f). Flat arguments are shown to every model with their descriptions. Several files means several calls in one turn. A model that sends the old nested shape with one file or one change is repaired (`harness/starter/args.ts`), as are other names for the same thing (`file`, `contents`, `start_line`); more than one is refused with the list of known arguments.

**`read`.** Returns numbered lines under a header that gives the file's version. Default window 2000 lines, plus the result cap; the result says how to ask for the rest with `offset`. A failed read is an error result. Directories return a listing.

**`write` and `edit`.** `write` creates or replaces a whole file (creating directories); its result gives the file's version, and a file that ended with a newline still does (whole-file writes often lose it; the result says when it was added). `edit` changes lines of an existing file by number. `read` numbers every line and shows the file's version (the word `version` and 8 hex digits of the content hash) in its header, and `edit` requires that version: a file that changed since is refused with "read it again", so line numbers can only be used on the file they came from. A call makes one change: `start`/`end` (inclusive) with `content` replacing those lines (empty or missing content deletes them), or `after` with `content` inserted after that line (0 is the top, the last line appends). The result echoes what was removed and added with the new line numbers, one unchanged line either side (so a doubled brace or a lost blank line shows), and the new version, so a following edit needs no re-read; working from the bottom of the file upwards keeps earlier numbers valid. A change is applied entirely or not at all. Line endings (CRLF) and a missing final newline are kept. Only whole lines can be replaced, which is fine for an edit tool. (`applyChanges` still applies several changes numbered as read, for callers that want it.) Both are `allow` by default because `/undo` rewinds files. (This replaced an anchor design after the first live run: see Step 4a.)

**`run` and `script`.** Two tools because they have different guarantees.

`run` takes one command line in a cross-platform, bash-like syntax with common shell utilities, plus whatever programs the host has. We parse the line ourselves (`harness/starter/command.ts`) and start the parsed programs directly, so no shell is involved and the approval prompt and the allowlist see programs and arguments, not a string. (This replaced an argv-list design after the live runs: models are fluent in shell syntax and kept getting nested lists wrong.) Supported: words with `'...'` and `"..."` quotes and backslash escapes (a backslash before an ordinary character stays literal, so Windows paths survive); `|` pipes; `<`, `>` and `>>` with workspace files (the same boundary and protected-file checks as `write`; `/dev/null` discards); unquoted `*`, `?`, `[...]`, `{a,b}` and `**` globs, expanded as a shell would against the workspace, confined to it, sorted, with no match an error (quoted wildcards are literal); `$NAME` and `${NAME}`, replaced from the host environment only for names listed under `tools.env` in `harness.yml` (a list, or `*`, which the CLI warns about; any other name is an error naming it; not inside single quotes); and `2>&1` and `2>/dev/null`, accepted because stderr is always shown with stdout. Refused, each with a message pointing to `script`: `;`, `&&`, `||`, `&`, backticks, `$(...)`, subshells, heredocs, process substitution, `VAR=x cmd`, a leading `~`, redirecting stderr to a file, and more than one line. The glob is a small one of our own over `Host.fs`, not a library: it has to work on whatever host the tools run on. **Windows.** The everyday utilities (`cat`, `ls`, `grep`, `sed`, `awk`, `head`, `tail`, `wc`, `sort`, `find`, `cp`, `mv`, `rm`, `mkdir`, `echo`, ... see `harness/starter/portable.ts`) do not exist there, or are different programs (`find`, `sort`), so on a Windows host the stage is started as `busybox.exe <applet> ...`; programs not on the list (`git`, `node`, `npm`) start as they are, nothing is added to PATH, and a path such as `./cat` is left alone. `busybox.exe` is GPL-2.0 and is not in the repository: `node tools/fetch-busybox.ts` downloads the xPack windows-build-tools release (or takes `--from` a zip or `--exe` a binary), checks it with `--list` and keeps it in `vendor/busybox/` (git-ignored); `findBusybox` also honours `CHATTREE_BUSYBOX`. Without it the model is told the utility is not available and what to use instead, instead of seeing "command not found".

`script` runs a string with `sh -c`, and the language is **POSIX sh on every platform**: `sh` on POSIX hosts, `busybox.exe sh` (ash) on Windows, and a clear "needs a POSIX shell" error if Windows has no busybox. Bash, python, PowerShell and the like are just programs the host may have, started with `run`. It always asks, no allowlist applies, and the CLI reports it as "running a script", not "calling a program".

Both run in the workspace root with stdin closed (unless redirected), a default timeout of 120 seconds (maximum 600) and their own process group, so a timeout or `/abort` kills everything they started. The result is the exit code, then stdout and stderr interleaved in arrival order, then a note if it timed out. The child inherits the user's environment minus anything the harness knows to be a secret, and secret redaction applies to results. These are the only tools that can reach outside the workspace.

### 4.2 Meta tools

**`subagent`** delegates a self-contained task. It calls `spawnSubagent` (fresh context: the child sees only the `brief`, plus a line saying how to hand back) and then **lets go**: a foreground call returns `waiting` (`ToolOutput.waiting`), the parent's loop stops as `blocked` and releases its lease, and the child's loop runs as a thread of its own, in the pump (5.4). Nothing about the child lives in memory: the call is `resumable`, and when the child has handed back the pump runs the parent again, the tool is called again, finds the child done, merges it and the merge entry answers the call. A foreground subagent is a context switch. A host that dies in the middle finds the same state in the transcripts.

The child ends its work by calling its own `merge {summary}` tool (a stateless report tool added by `subagentChildRegistry`), which ends its loop without another request. The report is read back from the child's transcript (`childState`: handed back, working, given up). A child that stops with text and has not been spoken to is sent one nudge by the pump (`subagentNudge`); a second text-only stop is "ended without handing its work back" and the call gets an error naming the branch. With `background: true` the call is answered at once (`started subagent <branch>`) and the report is delivered as a `subagent_result` merge when the child has handed back (`deliverSubagents`, called by the pump when the parent is free and by the loop before each request); a child that gave up becomes a failed `job_event`. What happens on finish is a `harness.yml` setting (`subagent.merge`), not the model's choice:

- `auto` (default): the child's `merge` has a standing yes (`subagentGrants`); `finishSubagent` merges with the trunk-wins policy and writes the `subagent_result` entry that answers the call. The model sees the child's report, the files that landed and any dropped on conflict.
- `review`: the child's `merge` call is a question in the queue (5.4) with the report in it. A refusal lets the child carry on; a yes ends it and the merge follows.

**Choosing the child's model.** With `subagent.models` in `harness.yml` (`provider/model` keys, each optionally with a `description` and a narrower `reasoning` list) the tool gets a `model` argument (an enum of those keys) and a `reasoning` argument (the union of the levels), and its description lists each choice with the catalog's description, its cost tier, its context window and its levels. Without the list nothing changes: no new arguments, the child uses the parent's model. The catalog is `ModelInfo` (`description`, `cost_tier` low/medium/high, `reasoning`: level name to the model settings that produce it, `default_reasoning`), bundled for the models we have prices for and overridable per field under `providers.<name>.models.<id>`. Levels have the same names for every provider and the catalog maps each to the adapter's own settings (`effort`, `thinking`, ...), so the parent never needs the adapter's words. The description has no prices, only the tier, so a price update does not change the pinned tool definition; a change to the list or the catalog does, and is accepted as `tools_changed` like any change to a tool. What the child gets (`harness/subagent-models.ts`): nothing chosen is the parent's setup as it is; another level of the same model is the parent's settings with the level's patch; another model starts from the output cap alone (the parent's other settings belong to the parent's model) plus the level (the model's default when none is asked for). A choice that cannot be built (a level the model lacks, no known output cap, settings the adapter refuses, a tool convention the child's tools do not fit) is a tool error before any branch is made, and a model from another provider has that provider's prices pinned in the child. A resumed child keeps the model it started with.

**Approval keys for `subagent`.** Without `subagent.models` the only key is `all`. With it a call's key is `inherit` (the parent's own model) or `provider/model@level` (`@default` when no level is asked for and the model has none), and a stored key may be a glob (`anthropic/claude-haiku-*@*`, `anthropic/*@low`), so a cheap model can be allowed without a dear one. `inherit` is never matched by a glob. Ordering by cost ("anything at tier 2 or below") is not built: it would need an ordering in the catalog, and the keys stay direct (docs/parking-lot.md).

**Spend.** A child's request is limited by the same ledger as the parent's: the child's branch contains the parent's history up to the spawn, so the turn and conversation figures it is checked against already include what the parent has spent (a test keeps this). What is not counted yet is the child's spend against the parent's limits while it runs (it arrives with the merge's rollup), which matters for a background subagent or several at once (docs/parking-lot.md).

The child gets the leaf tools but not the meta tools: no recursion, depth one. With `background: true` the call returns a job handle at once and the child runs meanwhile. In `auto` mode the eventual `subagent_result` has no open call to answer and the context builder already shows such an entry as a user message, so it is the notification; in `review` mode a `job_event` is written.

**`fork`** is for work to be picked up with everything the model already knows ("list the features, then fork a planning thread for each"). It creates a branch from the current point with the full history and returns at once with the branch name. `auto_run: false` (default): `message` is not sent but becomes the fork's prompt draft, waiting for the user to edit when they `/switch` there (drafts live in the CLI session today, so a fork's draft needs a persisted per-thread slot in the session store, not in history). `auto_run: true`: `message` is appended as the first user turn and the loop starts in the fork as a background job; when it finishes a `job_event` tells the parent. The user can `/switch` into a running fork to watch and `/abort` it; typing is blocked until it finishes because the branch is locked while a request runs. `fork` never merges.

**`merge`** brings a fork back with `mergeFork`: non-conflicting changes land, conflicting files keep this branch's version, a `fork_merge` entry records `summary`. Each merge reports only what is new since the last. It changes the parent's files, so it asks first.

Nested loops use the same code as the top-level loop with the child's conversation and its own tool context, so a child's tools can never write into the parent's worktree.

## 5. Safety

Three layers, in order of how much they can guarantee.

1. **Workspace boundary** (for `read`, `write`, `edit` and the `stdin`/`stdout` files of `run`). Paths are resolved against the worktree after following symlinks; anything outside is refused. Writing also refuses `chat.yml`, `harness.yml` and anything under `.git/` or `.chattree/`: a model that can rewrite `chat.yml` can rewrite history. `read` may read `chat.yml` but not the rest of `.git/`.
2. **Approvals.** See 5.1.
3. **What is not guaranteed.** An approved `run` or `script` runs with the user's permissions and can touch anything the user can; an allowlisted program can still do harm with the right arguments. Approval, not the boundary, is the safeguard there. An OS-level sandbox is the real fix and is the first follow-up; the registry's flags leave room for it.

File contents and command output are data and can contain instructions aimed at the model. No tool result can grant permission, change a policy or add an allowlist entry: those live in `harness.yml`, which `write` cannot touch, and in the user's terminal.

Child conversations get the leaf tools only, confined to their own worktree, with the same policies; a child's approvals are asked in the user's terminal, labelled with the child's name. A turn can create only a few branches (starting limit: 4 forks and subagents).

### 5.1 Approvals

A call runs without asking only if the tool's `allow` map in `harness.yml` holds an unexpired key that covers it; otherwise the host is asked. There is no `allow | ask | deny` setting: asking is what a missing key means, and a tool that is not listed is not offered to the model at all.

```yaml
tools:
  read:  { allow: { all: 2999-01-01 } }
  run:
    safe: [cat, grep, ls, git status, git diff]        # read-only prefixes, offered as `<prefix> **`
    allow: { "grep **": 2026-10-27T15:00:00Z, "node ./tools/*.ts": 2999-01-01 }
  script: {}                                            # no key can be granted: always asks
```

- **Keys and time.** A key is a class of operations, valued with the time it ends: a date (00:00 UTC) or a datetime with a zone, compared with the conversation clock. `all` covers every call. "Forever" is `2999-01-01`. "Once" stores nothing. Expired keys are ignored at once and dropped the next time the file is written. Unknown or malformed keys are ignored and never widen access.
- **The tool decides what a key means.** `Tool.allowKeys(args, ctx)` returns the keys a grant for this call would add (`null`: it can only be allowed once), `Tool.covers(keys, args, ctx)` returns the live keys that together cover a call (judged jointly, since a pipeline needs one per stage), `Tool.validateKey(key)` rejects keys that are not this tool's. A tool without the hooks can only ever be granted `all`.
- **Flow.** The loop checks each call after validation, one call at a time, so a grant made for the first call already covers the second. On a miss it asks the tool for keys and calls `approve({ callId, name, args, tool, keys })`. The host shows what will happen and answers `{ allow: true, grant?: { seconds, commit? } }` or `{ allow: false, reason? }`. A decline reaches the model as `The user declined to run this call: <reason>`. With keys the host may offer 5 minutes, 1 hour and forever; with `keys: null` only yes or no. If a grant comes with the answer the loop stores every key (`Conversation.grantStore`), and a key the tool will not accept is not stored while the approved call still runs once (the event says why). Without a host to ask (`approve` unset), a call no key covers is declined and never runs.
- **Where grants go.** The loop writes them to `harness.yml`, keeping comments; by default the change goes in with the next commit, and a forever grant (or `commit: true`) is a commit of its own holding only that file. A longer grant is never shortened by a shorter one. `harness.yml` is read afresh for each call, so a hand edit or `/tools` takes effect at once.
- **`read`, `write`, `edit`** offer `all`. **`script`** and **`merge`** offer nothing: the user sees the whole script or branch each time. A hand-written `all` for either is honoured; the host simply never offers it.
- **`run` keys** are one stage written as a command line, optionally with redirects: `grep **`, `git status **`, `node ./tools/*.ts`, `grep ** > ./**`. `*` as a whole word is any one argument and a last `**` any number. Any other word is a glob: `*` and `?` stay inside a path segment, `**` crosses them, and a candidate argument is covered when it matches, so `./**` is any workspace file. A candidate that is itself a glob is expanded first and covered when the files it names are; paths compare as `./relative`. A redirect (`< p`, `> p`, `>> p`) is allowed only when a key names it with a matching pattern; `>` also covers `>>`; `/dev/null` needs nothing. A pipeline is covered when each stage is covered by some live key.
- **What `run` offers.** For a command whose prefix is listed in `tools.run.safe` (`tools.run.safe` is read-only commands the user chose, so it is visible and editable), `<prefix> **`, with `<` and `>` clauses of `./**` when it redirects. For anything else the exact command as written, so what is granted is what was read. A key that would be a wildcard for a program that runs other programs (`xargs`, `env`, `sh`, `tee`, ...) is refused, and a wildcard key never covers a writing argument (`sed -i`, `sort -o`, `find -delete`, `--output`, ...).
- **Outside the workspace.** Any argument or redirect that resolves outside the workspace (symbolic links followed, `..`, absolute paths, `--opt=/path`) or onto an unreadable path is never covered by any key and is offered no key: it asks every time. It is not forbidden. Arguments that merely look like paths (`/pattern/` in `sed`) cost a prompt, nothing more.
- **Protection.** Only the loop acting on a host's answer, and the user, change grants. No tool result can: `harness.yml` is in the no-write list, the model never sees keys or expiries, only the decline text. `run` and `script` reach files through the shell, so the redirect check refuses protected targets and `script` is shown in full each time; grants are visible in git history.
- **Time and background work.** Expiry is checked when a call starts; a background job that began under a grant keeps running after it lapses.
- **Children.** A child conversation inherits a copy of its parent's `allow` maps at spawn; a grant made in a child stays in the child. Prompts always go to the user's terminal, labelled with the child's name.

### 5.2 Decisions in the thread, and the tip's state

An answer to an approval question is an `approval` entry (format 2.2): `{ call_id, allow, reason?, grant? }`, committed before the call's result. It is what lets one place ask and another answer. A call that a live grant covers has no entry, because that is decided by the grants and the clock; an entry exists only for a decision a person (or a host acting for one) made.

- **Where a grant lives.** A grant is kept in one place. `scope: "project"` (the default) is the `allow` map in `harness.yml`, as in 5.1, for every thread. `scope: "thread"` is the `grant` field of the entry: it covers matching calls later in this thread and in branches forked from it afterwards, and no other thread. A child's thread grant does not reach its parent; a parent's reaches children forked after it. The loop reads both when it checks a call, taking the later expiry for a key held twice.
- **The tip's state** (`foldTip`, `harness/tip.ts`) is worked out from the history, the config and the clock, the same way the model's context is, so every process that looks gets the same answer: `awaiting_user` (nothing owed), `ready` (a request to the model is owed), `run` (calls without a result that need nobody's decision: covered, approved, declined or invalid) and `needs_approval` (at least one call waits; `question` is the first). Appending an `approval` entry is the whole of answering.
- **Waiting.** With `waitForApproval` and no `approve`, the loop stops with `needs_approval` instead of declining, leaving the call and any after it without a result. Run again, it carries on with them: a call with a decision runs or is declined, one a grant covers runs, one still undecided stops it again. A host that has `approve` still asks in place; that is the fast path, and it writes the same entry.
- **Whether a call may have started** is not in the history; the run lease (5.3) says. Without `waitForApproval` the loop keeps its old rule: a call without a result is answered "did not run", except a declined call (nothing ran) and a resumable tool's. With it, calls carry on only if the lease the loop found was free (the last loop ended cleanly, by waiting); a lease left behind means the host died, and they are answered "did not run".

### 5.3 The run lease

Who is running a thread, and until when, is the run lease: one small file per thread in the repository's shared git directory (`chattree/leases/`), written by the host that runs it, never committed. It is separate from the append lock, which is held for one write: while a loop is mid-request another session can still append a user message or an approval.

- **Holds, each with a deadline.** `loop` while the loop works, `job:j1` for a background job, `call:<id>` and a followed thread for a call that waits on another thread. The lease is live until the latest deadline, and the file goes when the last hold does. The lease id is one per process and repository, so the loop and the jobs it started share one lease; the loop does not hold it while it waits for a person or after it stops, but a job does.
- **Every call has a time bound, so a live host never heartbeats.** The loop holds the lease for the request limit (`limits.max_request_seconds`, default 600) before a request and for the call's limit plus 30 s of headroom before a tool runs. A tool says how long a call may take with `Tool.timeout(args)`; the default is `limits.max_tool_seconds` (600). The loop stops a call that overruns by 5 s more (the tool gets that long to report its own timeout) and answers it with an error. A background job must say how long it may run (`started.lease: { seconds }`) and holds the lease that long. The one exception is waiting for a person in place: the lease is renewed while the question is up.
- **A thread that waits for another follows it, or lets go.** `Tool.timeout` can be `"thread"` (a background job says `started.lease: { follows }`): the call then names the thread it waits for (`ctx.lease.follow(branch)`) and is live exactly as long as that thread's lease is, plus a grace of 30 s for it to start. A foreground `subagent` does neither: it returns `waiting`, and the parent holds nothing while the child works (5.4); the child's own lease says that work is running.
- **State.** `free`: nothing is running and the last run ended cleanly. `live`: a loop or job holds it (`Conversation.leaseState()`, and the tip's `running`). `stale`: past its deadline, or its owner is known to be dead, which the CLI works out for a process on this machine by asking whether the pid exists. A stale lease is taken over by whoever asks next, who is told so; calls without a result under it are `lost` in the tip's fold and answered "did not run".
- **Another process that holds it** makes a new loop fail at once with `ThreadBusy`, naming the session or process. Interrupting is in-process only: a stuck loop in another process is dealt with by killing that process, after which its lease is stale at once. A lease that is only a file cannot span clones. When that is wanted the same `LeaseStore` interface can sit on a ref (`refs/chattree/leases/<branch>`, updated with an expected old value and pushed), which is atomic and leaves nothing in the transcript.

### 5.4 Questions, the pump and who runs what

A question is a thread whose tip needs a decision, so the question queue is the set of such threads, worked out by reading transcripts. `harness/pump.ts` is the one place that does it. A `Pump` is given a way to open threads and to run one (`loop`), looks at each thread, folds its tip (`foldTip`) and acts:

- `running` (a live lease, in this process or another) and `blocked` (a call waits for a thread that is still working, `Tool.waitingOn`): nothing.
- `needs_approval`: the question is added to `pump.questions()`. `pump.answer(branch, callId, decision)` re-reads the thread, refuses a call that is already decided or answered (the first answer wins; the other host is told), writes the `approval` entry, saves a project grant to `harness.yml`, and looks at the thread again. Whoever answers starts the loop: there is no lease to hand over.
- `run` (calls decided, covered or declined): the loop runs. After a subagent hands back, the parent's call stops being `blocked` and this is what restarts it.
- `ready`: run, by what made the request owed (`TipState.ready.cause`). `human` (a user message, or the brief a subagent or fork was started with): somebody asked, so it runs, whichever process appended it; a message and an answer are the same kind of mutation. `event` (a job ended, a subagent or fork reported): nobody asked, so it runs only when the host says so (`resume` hook, from `background.resume`). `result` (a tool result is the last entry): the loop that was answering it did not finish; left alone. `awaiting_user`: `idle` may send a message (the one nudge).
- A thread the screen has (`leave`): its questions are collected, but the pump does not start it; it says so (`onWanted`) and the screen runs the turn, so the output shows as a turn does.

A loop that ended because it was stopped, timed out or failed is **held**: left alone until released (`release`; `/runs say` does), so a stuck thread is not run again in a circle. Loops that completed, finished, waited for a decision or blocked cause a fresh look at every thread, since a thread finishing is what the one waiting for it needs. `watch()` compares branch tips every second or so and sweeps everything now and then (a lease running out is a change nothing writes down), so an answer made by another process is seen. Parent and child loops can run at once; a child's question appears while the parent is blocked.

The CLI owns one pump per session (`Engine.pump()`). Subagents' loops run in it, with `waitForApproval` and the project's grants. The main thread's own turn no longer asks in place: `runTurn` sets `waitForApproval`, a call no grant covers ends the turn (`waiting for your answer`), and the question waits with the others. When the terminal is idle it asks them one at a time, each labelled with its thread when that is not the current one, and keeps what was half-typed. A thread is run again when its answer is recorded; the current thread's turn is started by the terminal. Ctrl-C at a question answers no and ends that turn (the call is answered "did not run", no request follows); for another thread it holds it. A message already waiting when a session first looks at its thread (a send that was refused, or left over) is the user's to send (`/retry`); one that arrives or is answered afterwards runs by itself. A turn that was stopped, refused or failed holds its thread until the next message or `/retry`. Without a terminal (a pipe) questions are declined with a reason, as before.

**Forks that run by themselves.** `fork {auto_run: true, message}` pins the fork's tools to the leaf set, puts the message in the fork and returns `started fork <branch>.`; the pump runs it like any thread that has been spoken to, its questions join the queue, and `deliverForks` reports its first run's end to the caller as a `job_event` (once). Only a thread whose pinned tools are exactly the child set is run when the user is not on it, so ordinary forks are left to their user.

**`chattree run`** is the pump with no screen (`cli/run.ts`): it looks at every thread, runs what needs nobody, and leaves questions in the transcripts for any session to answer, noticing the answer by the same polling. By default it keeps watching until stopped; `--once` does what can be done and leaves with status 0 (nothing waiting), 3 (questions waiting) or 1 (a thread was held after a failure). It logs tool calls and new questions to standard error (`waiting on <thread>: allow ... (chattree chat -t <thread>)`). `/thread <name>` on a thread that has a run in the pump shows what it is doing; `/runs` lists the pump's runs with the tool set's.

## 6. CLI experience

- **Tool activity.** Each call is a start line with a one-line summary (`read src/cli/turn.ts`, `run pnpm test`) and a result line with outcome, size and time plus a short preview. `/expand [n]` shows the full output using the entry refs `/log` understands. Errors and declined calls are styled as errors; the plain renderer prints the same without colour.
- **Nested and background work.** A foreground `subagent` is an indented block under its call, lines prefixed with the child's branch name, with a one-line summary at the end. Anything in the background prints one line when it starts and shows no live output; `/jobs` or switching into the fork shows it.
- **Approvals.** `Io.ask` with a fixed menu: `y` once, `n` (then an optional reason), and when the tool offered keys `5` (5 minutes), `h` (1 hour) and `f` (forever), each showing the keys it would add. The question is asked when the terminal is idle (5.4), labelled with the thread it belongs to; half-typed text is kept. Without a terminal an uncovered call is declined.
- **Stopping.** `/abort` and Ctrl-C stay `allowed` while the loop runs and stop the request or tool and end the turn.
- **Background notifications.** A finished job is always committed. By default the CLI shows a line at the prompt; with `background.resume: true` a request is also sent. Opt-in because it spends money unattended, and every limit still applies.
- **Commands.** `/tools` lists each tool with its live keys and when they end; `/tools <name> allow [key] [duration]` adds a key (default `all`, forever) and `/tools <name> revoke [key]` removes one or all, through `Conversation.grantStore` and `revokeGrant`. `/jobs` and `/jobs stop <id>`. `/undo`, `/log`, `/retry`, `/continue` and `/export` work on tool entries unchanged. A fork with a waiting draft shows in `/threads`.
- The one-shot `ask` command stays tool-free.

## 7. Settled in review

- `fork` returns immediately; `auto_run` chooses draft or background run.
- `subagent` has `auto` and `review` modes, set in `harness.yml`.
- Approvals are `allow` maps of key to expiry in `harness.yml` (5.1); `read`, `write` and `edit` start with `all: 2999-01-01`, everything else asks.
- `run` takes a bash-like command line that we parse (no shell), with busybox standing in for the everyday utilities on Windows; `$VAR` only for names in `tools.env`; globs expand as in a shell; `script` (POSIX sh) is the escape hatch.

- Large output: a reference when the repository holds it, a blob otherwise.
- Background tools via an asynchronous executor, `job_event`, and the job tools; idle resume opt-in.
- A child's cost counts toward the parent's turn limit.

- **Busybox on Windows (`tools.run.busybox`).** `run` and `script` get their utilities (cat, ls, grep, sh…) from busybox.exe on Windows. `tools.run.busybox` is `auto` (the default), `off` or a path. `auto` uses a busybox.exe that is already there (`CHATTREE_BUSYBOX`, else vendor/busybox/) and otherwise fetches the pinned xPack release (`hosts/busybox.ts`: URL and zip SHA-256 pinned in `BUSYBOX_RELEASE`, the exe must answer `--list` like busybox, the user is told before the download). A failure (no network, wrong hash, no pin) is a `BusyboxError`, shown by the CLI as an error with a hint *before the message is sent*, so the model never sees it; the tool set is rebuilt on the next try. `off` never fetches and the model is told the utility is not available. `node tools/fetch-busybox.ts` does the same by hand. Pinned: zip sha256 113d4dfd…d218 (2,688,306 bytes, v4.4.1-3 win32-x64). Without busybox, take `run` and `script` out of `tools` in harness.yml: only listed tools are offered to the model, and `init` lists every built-in one. Not yet run on a real Windows machine.

- **Windows batch programs (`tools.run.batch`).** On Windows `run` starts programs without a shell, so `npm`, `pnpm` and other `.cmd` or `.bat` programs were not found (and Node refuses to spawn them directly since CVE-2024-27980, because `cmd.exe` re-reads the command line and treats `% ^ & | < > " !` as syntax whatever the quoting). They are now found but refused by default with a message naming the setting. With `tools.run.batch: true` in `harness.yml` they start as `cmd.exe /d /s /c ""file" args"` with verbatim arguments (`RunSpec.verbatim`), and any argument containing one of those characters, a line break or NUL is refused rather than escaped. Lookup is plain: a bare name is searched along `PATH` in order (relative entries resolve from the workspace; the bare current directory is not searched; `.com`, `.exe`, `.bat`, `.cmd` in that order per directory), and a name with a path or batch extension resolves from the workspace. Only at the end is the result checked: if the batch file resolves inside the workspace (after following links) it must match a glob in `tools.run.local` (for example `./node_modules/.bin/*.cmd`; compared as `./relative`, case-insensitive), otherwise it is refused with that specific reason. Batch files outside the workspace are not held to the list. `hostEnv` (`PATH`, `ComSpec`) comes from the CLI's environment. Written and unit-tested on Linux with a host that reports `windows`; not yet run on a real Windows machine.

- **Step 8d (`fork` and `merge` tools).** `harness/fork-tools.ts`. `fork {name?, message?}` makes a branch from the current point (`createFork`, supplied by the CLI so the worktree goes where the project keeps them; unnamed forks are `fork/N`) and returns at once. - **Step 8 revision: runs, finishing by `merge`, recovery, `review`, `background`.** `harness/runs.ts`: `ThreadRuns` owns the loops running in this process; a `Run` belongs to a branch, goes through cycles (one `runLoop` each; `running`, `idle`, `closed`), has `subscribe` (with replay), `cycleEnd`, `resume`, `abort` and `close`. The CLI's toolset holds one `ThreadRuns`, closed on exit. `subagent` is now built on it. The child ends its work by calling its own `merge {summary}` tool, which returns `finish: true` (new `ToolOutput` flag: the loop records the result, answers later calls of that response as not run, makes no further request and returns status `finished`); the caller then merges with `finishSubagent` and the merge entry answers the call. A child that ends a cycle with a plain reply is nudged once; if it still does not report, and the user never spoke in its branch, the call fails with the branch named (nothing merged). If the user stopped it or spoke in it, the call stays open until the child reports or the run is closed (`/stop` and attaching to a running branch are the CLI work still to do; the library side is tested by resuming the run by hand). The brief always ends with how to hand back. **Recoverable:** the branch is `sub/<label>-<hash of the call id>`; a new `Tool.resumable` flag lets the loop run an unanswered call of such a tool again at start (instead of "did not run"), the tool finds its branch (and gives it a setup if the crash came first) and carries on. **`review`:** `subagent.merge: review` in harness.yml makes the child's `merge` call ask the user, with the report in the question; a refusal (with a reason) lets the child carry on. **`background: true`:** the call returns at once with a job; `StartedJob.started.settle` runs when the job's event would be committed (between requests), merges with `finishSubagent`, and that entry reports the job, so no `job_event` is written (and `recover` knows such a job is not lost). A crash while a background subagent runs marks the job lost, as for any job; its branch remains for `/merge`. - **Architecture step 4 (the headless pump).** The pump runs a `ready` tip by cause (`human` runs, `event` only with `background.resume`), so a message is the same kind of mutation as an answer. A chat session and a runner on the same thread can both try to start it after an answer; the loser gets `ThreadBusy` and says so.
